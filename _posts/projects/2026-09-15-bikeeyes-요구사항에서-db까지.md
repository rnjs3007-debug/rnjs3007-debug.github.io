<p>BikeEyes 프로젝트에서 AI 모델 개발을 담당하면서 요구사항 정의서, 기능 처리도, 알고리즘 명세서, 프로그램 목록, 테이블 정의서를 주도적으로 작성했다.</p>
<p>이 문서들은 최종 보고서를 제출하기 위해 마지막에 한꺼번에 만든 결과물이 아니다. 프로젝트 초반부터 앱·서버·AI의 역할과 데이터 흐름을 정리하고, 요구사항마다 ID를 붙여 구현 기준을 잡았다. 정상 흐름뿐 아니라 네트워크 단절, GPS 정확도 저하, AI 미탐처럼 실제 주행 중 발생할 수 있는 예외 상황도 함께 정의했다.</p>
<p>물론 처음 작성한 내용이 끝까지 그대로 유지된 것은 아니었다.</p>
<p>실제 데이터를 수집하고 모델을 학습한 뒤 앱과 서버를 연결해보니, 설계 단계에서는 보이지 않던 문제가 나타났다. crack을 BBOX로 표현하는 방식에는 한계가 있었고, AI 결과와 센서 데이터를 결합하는 기준도 실제 수집 주기에 맞춰 다시 검토해야 했다. 전송 실패 시 재시도 흐름이나 GPS 정확도가 낮은 데이터의 처리 방식처럼 구현하면서 더 구체적으로 정해야 한 부분도 있었다.</p>
<p>그때마다 구현만 고치고 끝내지 않았다. 변경된 기준이 요구사항 정의서, 기능 처리도, 알고리즘 명세서, 프로그램 목록, DB 구조에 빠짐없이 반영되도록 관련 문서를 함께 수정했다.</p>
<p>이 글에서는 처음 세운 요구사항이 실제 구현을 거치며 어떻게 구체화됐고, 하나의 기술 변경이 여러 설계 문서와 DB 구조까지 어떻게 이어졌는지를 정리한다.</p>
<blockquote>
<p><strong>초기 요구사항 수립 → 구현 및 검증 → 문제 확인 → 기준 변경 → 관련 문서와 DB 구조 동기화</strong></p>
</blockquote>
<h2 id="1-프로젝트-초반-문서-체계-잡기">1. 프로젝트 초반, 문서 체계 잡기.</h2>
<p>BikeEyes는 Android 앱, 서버, AI 모델이 서로 연결되는 구조다.</p>
<pre><code class="language-text">Android 앱  →  카메라·GPS·센서 수집, Room 저장, 서버 동기화
서버         →  AI 분석 요청, 위험구간 판정, API 제공
AI 모델      →  BBOX·Segmentation 기반 위험요소 분석
DB           →  분석 결과와 위험 이벤트 저장</code></pre>
<p>나는 AI 모델 학습만 담당한 것이 아니라, 프로젝트 초반부터 전체 기능이 어떤 순서로 연결되는지 문서로 정리했다. AI가 어떤 값을 출력하는지만 적는 것으로는 부족했다. 서버가 그 값을 어떤 형식으로 받고, 어느 테이블에 저장하며, 앱이 어떤 조건에서 사용자에게 보여줄지까지 연결해야 했기 때문이다.</p>
<p>예를 들어 요구사항 정의서에 적힌 ‘위험요소를 탐지한다’는 문장을 실제 기능으로 만들려면 다음 항목이 필요했다.</p>
<ul>
<li>어떤 모델이 분석하는가?</li>
<li>탐지 대상 클래스는 무엇인가?</li>
<li>confidence는 어떤 기준으로 판정하는가?</li>
<li>탐지 결과와 GPS·센서 데이터는 어떻게 연결하는가?</li>
<li>같은 위치에서 반복된 탐지는 어떻게 누적하는가?</li>
<li>최종 결과는 DB의 어느 테이블과 컬럼에 저장하는가?</li>
<li>유효한 탐지가 없거나 전송에 실패하면 어떻게 처리하는가?</li>
</ul>
<p>이 질문에 대한 기준을 먼저 문서로 잡고, 팀원들과 구현 범위를 맞췄다. 문서는 단순한 설명 자료가 아니라 앱·서버·AI가 같은 기준으로 개발되기 위한 출발점이었다.</p>

<p>ID를 붙인 이유는 문서를 보기 좋게 만들기 위해서가 아니었다. 회의할 때 “그 AI 판독 기능”이라고 부르는 대신 A01_B01이라고 말할 수 있게 하려는 것이었다.</p>
<p>기능 이름만으로 이야기하면 사람마다 떠올리는 범위가 달랐다. 같은 ID를 사용하니 어느 요구사항을 말하는지 바로 확인할 수 있었고, 기능 처리도와 프로그램 목록에서도 해당 기능을 계속 추적할 수 있었다.</p>
<p>나중에 기능이 변경됐을 때도 ID가 기준이 됐다. 변경된 요구사항과 연결된 흐름도, 프로그램, 테이블을 역으로 찾아 수정할 수 있었다.</p>

<p>예를 들어 GPS 정확도가 낮은 데이터를 단순히 ‘별도 처리’한다고 적는 것만으로는 부족했다. 실제 흐름에서는 해당 데이터를 위험구간의 근거로 누적할지, 저장만 할지, 다음 수집 주기로 넘길지를 분명히 정해야 했다. 이런 부분은 구현 결과를 확인한 뒤 기능 처리도와 알고리즘 명세서에서 다시 구체화했다.</p>

<h2 id="5-초기-설계의-구체화">5. 초기 설계의 구체화</h2>
<p>프로젝트 초반에 요구사항과 처리 구조를 잡았지만, 실제 구현이 시작된 뒤에는 여러 번 수정이 필요했다.</p>
<p>설계가 잘못돼서 전부 다시 작성한 것은 아니었다. 초기 문서가 전체 방향과 역할을 잡는 기준이었다면, 구현 단계의 수정은 실제 데이터와 코드에서 확인한 내용을 반영해 기준을 더 정확하게 만드는 과정에 가까웠다.</p>
<p>변경이 생기면 다음 순서로 확인했다.</p>
<pre><code class="language-text">실제 구현 또는 테스트
        ↓
초기 요구사항과 다른 점 확인
        ↓
처리 조건과 예외사항 재정의
        ↓
관련 문서와 DB 구조 수정
        ↓
팀원에게 변경 기준 공유</code></pre>
<p>이 과정을 반복하면서 문서는 프로젝트 초기에 한 번 쓰고 보관하는 자료가 아니라, 실제 구현 상태를 따라가는 기준 문서가 됐다.</p>
<h2 id="6-crack-처리-방식-변경">6. crack 처리 방식 변경</h2>
<p>가장 큰 변경 사례는 crack의 처리 방식이었다.</p>
<p>초기에는 crack도 다른 위험요소와 함께 BBOX Detection 대상으로 구성했다. 하지만 실제 데이터를 학습하고 주행 영상을 검증해보니, 길고 불규칙한 균열을 사각형으로 표현할 경우 정상 노면까지 넓게 포함되는 한계가 있었다.</p>
<p>그래서 crack을 <code>linear</code>와 <code>alligator</code>로 구분하고, 픽셀 단위의 Segmentation 문제로 다시 정의했다. 포트홀, 맨홀, 침수구간, 볼라드는 BBOX Detection으로 유지했다.</p>
<p>이 결정은 모델 코드 하나를 바꾸는 것으로 끝나지 않았다.</p>

<h2 id="7-서비스-판정-기준-보완">7. 서비스 판정 기준 보완</h2>
<p>AI 결과가 그대로 사용자 화면에 표시되는 것은 아니다. 모델 추론 이후에도 유효 탐지 판정, GPS·센서 데이터 결합, 동일 위치의 근거 누적, 위험구간 확정 과정이 이어진다.</p>
<p>초기 문서에서는 이 흐름의 큰 기준을 정했고, 실제 모델 결과와 수집 데이터를 확인하면서 세부 조건을 보완했다.</p>
<h3 id="1-클래스별-confidence-기준">1) 클래스별 confidence 기준</h3>
<p>모든 클래스에 동일한 confidence 기준을 적용하지 않고, 검증 데이터에서 클래스별로 threshold를 변경하며 Precision, Recall, F1-score의 변화를 확인한 뒤 운영 기준을 따로 설정했다.</p>
<pre><code class="language-text">pothole      0.50
manhole      0.55
flood_area   0.50
bollard      0.55
linear       0.40
alligator    0.40</code></pre>
<p>포트홀, 맨홀, 침수구간, 볼라드는 잘못된 위험정보가 사용자에게 전달되는 것을 줄이기 위해 오탐을 비교적 엄격하게 걸러내는 방향으로 0.50~0.55를 적용했다.</p>
<p>반면 linear와 alligator는 형태가 길고 불규칙해 실제 주행 이미지에서 confidence가 상대적으로 낮게 나타나거나 일부 균열을 놓치는 경우가 있었다. 따라서 균열 계열은 Recall을 함께 고려해 기준을 0.40으로 설정했다.</p>
<p>이 값들은 임의로 정한 것이 아니라 클래스별 threshold 변화에 따른 Precision·Recall·F1-score와 실제 주행 영상의 오탐·미탐 사례를 함께 확인해 결정한 운영 기준이다.</p>
<p>서버에는 최종 숫자만 전달하지 않았다. 어떤 클래스에 어떤 기준을 적용하는지, 기준 미만 결과는 어떻게 처리하는지, 관리자가 직접 등록한 결과와 AI 탐지 결과를 어떻게 구분하는지도 문서에 함께 정의했다.</p>
<h3 id="2-ai가-탐지하지-못한-경우">2) AI가 탐지하지 못한 경우</h3>
<p>AI의 유효 탐지가 없더라도 센서에서 위험 가능성이 확인되면 이미지를 바로 삭제하지 않고 관리자 재검토 대상으로 분기하도록 했다.</p>
<pre><code class="language-text">AI 유효 탐지 없음
        ↓
센서 조건 확인
        ↓
조건 충족   → 관리자 재검토 항목 생성, 이미지 삭제 보류
조건 미충족 → 기존 객체 없는 이미지 처리 정책 적용</code></pre>
<p>이 부분도 구현하면서 분기 위치와 데이터 처리 범위를 계속 확인했다. AI 결과, 이미지, 센서값, 위치값이 각각 따로 처리되는 것이 아니라 하나의 이벤트 근거로 연결되어야 했기 때문이다.</p>
<h3 id="3-관리자가-직접-등록한-결과">3) 관리자가 직접 등록한 결과</h3>
<p>관리자가 이미지를 검토해 위험요소를 직접 등록한 경우에는 confidence를 <code>NULL</code>로 저장하도록 했다.</p>
<p>사람이 판단한 결과에 AI confidence를 임의로 넣으면 이후 평균 confidence 계산의 의미가 달라진다. 그래서 관리자 등록 건은 AI confidence 평균에서는 제외하되, 서로 다른 주행의 근거 횟수에는 포함할 수 있도록 구분했다.</p>
<p>이처럼 구현 단계에서는 ‘값을 저장한다’는 요구사항보다 '그 값이 어떤 의미를 가지며 이후 계산에서 어떻게 사용되는지'까지 정해야 했다.</p>
<h2 id="8-변경사항-추적과-문서-반영">8. 변경사항 추적과 문서 반영</h2>
<p>구현 중 기준이 바뀌면 한 문서만 수정해서는 안 됐다.</p>
<p>예를 들어 AI 분석 방식이 변경되면 요구사항 정의서의 설명뿐 아니라 기능 처리도의 흐름, 알고리즘 명세서의 분기, 프로그램 목록의 기능명, 테이블 정의서의 컬럼 구조까지 확인해야 했다.</p>
<p>반대로 앱의 수집 주기나 서버 전송 방식이 달라지면 AI와 센서 데이터를 결합하는 기준에도 영향이 있는지 다시 확인해야 했다. GPS 정확도가 낮은 데이터를 제외하는 위치나, 네트워크 실패 시 재전송하는 주체가 앱인지 서버인지도 흐름도에서 명확하게 구분해야 했다.</p>
<p>이때 문서를 완벽하게 처음부터 작성하는 것보다 중요했던 건 변경된 구현을 문서에 빠뜨리지 않는 일이었다.</p>
<p>초기 요구사항은 개발 방향을 잡는 기준이었고, 이후 수정 이력은 실제 구현에서 무엇이 달라졌는지를 보여주는 기록이었다. 두 가지가 함께 있어야 최종 문서가 단순한 계획서나 사후 정리본이 아니라 실제 프로젝트의 흐름을 설명할 수 있었다.</p>
<h2 id="9-연구환경과-서비스환경-분리">9. 연구환경과 서비스환경 분리</h2>
<p>AI 학습과 서비스 운영을 분리하는 내용은 <code>A08_B01</code> 요구사항으로 따로 관리했다.</p>
<pre><code class="language-text">- AI 모델 학습 및 비교 실험은 서비스 시스템과 분리된 연구환경에서 수행
- 검증을 마친 BBOX 및 Segmentation 모델만 서버 서비스에 적용
- 비교 실험 후 제외한 알고리즘은 서비스 배포 대상에서 제외</code></pre>
<p>실험 중인 모델이 서비스에 바로 반영되면 성능 문제가 발생했을 때 원인이 모델인지 서버 코드인지 구분하기 어렵다. 여러 모델을 비교하는 동안에도 서비스에는 검증을 마친 모델만 적용하도록 경계를 정했다.</p>
<p>이 기준은 실제 모델 학습 과정에서 라벨 오염으로 성능이 크게 떨어지는 문제를 경험한 뒤 더 중요해졌다. 데이터나 모델의 문제를 해결하는 과정과 서비스에 적용하는 과정을 분리해야 오탐 결과가 사용자 화면까지 그대로 전달되는 일을 막을 수 있었다.</p>
<h2 id="10-문서-작성의-역할과-성과">10. 문서 작성의 역할과 성과</h2>
<p>문서 작성을 맡았다고 해서 다른 팀원의 구현을 대신한 것은 아니다. 내가 한 일은 각 담당자의 구현 내용을 받아 적는 데 그치지 않고, 앱·서버·AI 사이에서 합의한 기준을 하나의 흐름으로 연결하는 것이었다.</p>
<p>AI 출력 형식이 달라지면 서버와 DB에 어떤 영향이 있는지 확인했고, 앱의 수집 방식이 바뀌면 AI 분석에 필요한 데이터 결합 조건을 다시 살폈다. 기준이 불분명한 부분은 팀원들과 확인한 뒤 요구사항과 예외사항으로 정리했다.</p>
<p>문서를 직접 관리하니 변경의 영향 범위도 더 잘 보였다.</p>
<ul>
<li>요구사항 ID를 기준으로 관련 기능과 프로그램을 찾을 수 있었다.</li>
<li>정상 흐름과 예외 상황이 다르면 기능 처리도에서 분기 위치를 다시 확인할 수 있었다.</li>
<li>AI 출력 형식이 바뀌면 테이블의 컬럼과 NULL 허용 여부까지 점검할 수 있었다.</li>
<li>구현과 문서가 다를 때 어느 쪽을 최종 기준으로 정할지 팀원들과 구체적으로 이야기할 수 있었다.</li>
</ul>
<p>프로젝트 후반에는 팀원이 반복해서 묻는 내용도 문서의 빈 부분을 찾는 기준으로 삼았다. 질문에 그때그때 답하는 데서 끝내지 않고, 같은 질문이 다시 나오지 않도록 요구사항이나 예외사항을 보완했다.</p>
<h2 id="11-마무리">11. 마무리</h2>
<p>이번 프로젝트에서 설계 문서를 작성한 경험은 정해진 양식에 내용을 채워 넣은 작업과는 달랐다.</p>
<p>프로젝트 초반에는 요구사항과 ID 체계, 역할, 데이터 흐름, 예외 처리의 기본 기준을 직접 잡았다. 이후에는 실제 데이터 수집과 모델 학습, 앱·서버 구현 과정에서 확인된 변경사항을 관련 문서와 DB 구조에 계속 반영했다.</p>
<p>초기 설계와 최종 구현이 완전히 같지는 않았다. 하지만 그 차이를 실패라고 생각하지 않는다. 실제 구현을 통해 더 정확한 기준을 찾았고, 무엇이 왜 바뀌었는지를 문서로 추적할 수 있었기 때문이다.</p>
<p>특히 crack을 BBOX에서 Segmentation으로 변경한 경험을 통해, AI 모델의 기술적 판단 하나가 알고리즘과 서버 처리 흐름, DB 저장 구조까지 이어진다는 것을 확인했다. 반대로 앱이나 서버의 변경도 AI 데이터 처리 기준에 영향을 줄 수 있었다.</p>
<p>결국 이 프로젝트에서 내가 주도한 문서 작업의 핵심은 문서를 많이 만든 것이 아니었다.</p>
<blockquote>
<p><strong>초기에 구현 기준을 세우고, 실제 개발 과정에서 달라진 내용을 추적해 앱·서버·AI가 다시 같은 기준을 바라보게 만든 것.</strong></p>
</blockquote>
<p>AI 모델의 결과가 실제 서비스 기능으로 연결되기까지 필요한 흐름을 설계하고, 구현 변화에 맞춰 그 흐름을 끝까지 관리해본 경험이었다.</p>
