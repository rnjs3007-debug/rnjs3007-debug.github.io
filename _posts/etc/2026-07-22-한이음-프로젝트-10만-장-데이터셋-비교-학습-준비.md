<p>자전거도로 위험요소 탐지 대상을 여러 번 수정한 끝에, 최종적으로 다음 5개 클래스를 사용하기로 했다.</p>
<pre><code class="language-text">0 manhole
1 pothole
2 flood_area
3 bollard
4 crack</code></pre>
<p>클래스를 정하고 나니 드디어 바로 학습을 시작할 수 있을 것 같았다.</p>
<p>하지만 실제로는 그다음 과정이 훨씬 더 오래 걸렸다. 원본 데이터의 형식이 서로 달랐고, 클래스마다 이미지 수 차이도 컸다. 어떤 데이터는 바운딩 박스로 표시돼 있었고, 어떤 데이터는 폴리곤이나 선 형태로 라벨링돼 있었다.</p>
<p>이번 프로젝트에서는 YOLO만 사용하는 것이 아니라 YOLOv8m, YOLO11m, RT-DETR-L, EfficientDet-D3, RetinaNet, Faster R-CNN 6개의 여러 객체 탐지 모델을 비교할 계획이었다.</p>
<p>그러려면 같은 원본 데이터를 각 모델이 읽을 수 있는 형식으로 변환하고, 학습·검증·테스트 데이터도 최대한 동일하게 유지해야 했다.</p>
<hr />
<h2 id="1-원본-데이터-구조-확인">1. 원본 데이터 구조 확인</h2>
<p><img alt="" src="https://velog.velcdn.com/images/addung/post/3b9260ed-cda7-4c41-a045-871713f257b6/image.png" /></p>
<p>프로젝트에 사용한 맨홀, 포트홀, 침수구간, 볼라드 데이터는 AI Hub 데이터를 중심으로 구성했다.</p>
<p>애증의 'crack' 데이터는 Roboflow에서 공유된 여러 국가의 데이터를 함께 사용했다.</p>
<p>문제는 데이터마다 라벨 구조가 조금씩 달랐다는 점이다.</p>
<p>예를 들어 AI Hub의 일부 원본 라벨은 JSON 안에 다음과 같은 바운딩 박스 좌표가 들어 있었다.</p>
<pre><code class="language-text">[x, y, width, height]</code></pre>
<p>반면 YOLO는 다음과 같은 정규화 형식을 사용한다.</p>
<pre><code class="language-text">class_id x_center y_center width height</code></pre>
<p>원본 JSON은 이미지의 실제 픽셀 좌표를 사용하지만, YOLO 라벨은 모든 좌표를 이미지 크기로 나눈 <code>0~1</code> 사이의 값으로 저장한다.</p>
<p>예를 들어 가로 1920픽셀 이미지에서 객체 중심이 960픽셀 위치에 있다면 다음처럼 계산된다.</p>
<pre><code class="language-text">x_center = 960 / 1920 = 0.5</code></pre>
<p>처음에는 라벨 파일의 확장자만 바꾸면 되는 줄 알았다. 하지만 실제로는 좌표 체계까지 함께 변환해야 했다.</p>
<p>이미지와 라벨의 파일명이 정확히 연결되지 않거나 좌표 계산이 틀리면, 학습 자체는 실행되더라도 모델은 잘못된 위치를 객체라고 배우게 된다.</p>
<p>그래서 원본 JSON을 읽고 YOLO 형식의 txt 라벨로 변환하는 코드를 작성해 데이터셋을 준비했다.</p>

<h2 id="2-클래스별-데이터-수량-점검">2. 클래스별 데이터 수량 점검</h2>
<p>원본 데이터를 확인해 보니 클래스마다 확보된 이미지 수가 크게 달랐다.</p>
<p>어떤 클래스는 이미 2만 장을 넘었지만, 어떤 클래스는 1만 장 안팎에 그쳤다.</p>
<p>이 상태로 그대로 학습하면 이미지가 많은 클래스를 모델이 더 자주 보게 되며 반대로 데이터가 적은 클래스는 상대적으로 학습 기회가 줄어들 수 있다.</p>
<p>그래서 비교 실험에서는 모든 클래스의 데이터 수를 약 2만 장으로 맞추기로 결정하였다.</p>
<pre><code class="language-text">클래스당 목표: 20,000장
전체 목표: 100,000장</code></pre>
<p>최종 클래스가 5개였기 때문에 전체 데이터셋은 약 10만 장 규모가 됐다.</p>
<p>2만 장을 넘는 클래스는 필요한 수량만 무작위로 선택했고, 부족한 클래스는 이미지 증강을 통해 보충했다.</p>

<h2 id="3-데이터-증강-및-라벨-동기화">3. 데이터 증강 및 라벨 동기화</h2>
<p>데이터가 부족한 클래스는 이미지 증강을 사용했다.</p>
<p>처음 떠올린 방법은 밝기 조정, 좌우 반전, 회전, 크기 변경 등이었다.</p>
<p>그런데 객체 탐지는 이미지 분류와 달리 객체의 위치까지 학습한다. 이미지를 움직이면 바운딩 박스 좌표도 같은 방식으로 함께 바뀌어야 했다.</p>
<p>예를 들어 이미지 좌우를 뒤집으면 오른쪽에 있던 포트홀이 왼쪽으로 이동한다. 이때 이미지만 뒤집고 기존 라벨을 그대로 사용하면, 모델은 실제 객체가 없는 위치를 포트홀이라고 배우게 된다.</p>
<h3 id="가-좌표를-바꾸지-않아도-되는-증강">가. 좌표를 바꾸지 않아도 되는 증강</h3>
<ul>
<li>밝기 조정</li>
<li>대비 조정</li>
<li>색감 조정</li>
<li>약한 블러</li>
<li>노이즈 추가</li>
</ul>
<h3 id="나-좌표도-함께-바꿔야-하는-증강">나. 좌표도 함께 바꿔야 하는 증강</h3>
<ul>
<li>좌우 반전</li>
<li>상하 반전</li>
<li>회전</li>
<li>크기 조절</li>
<li>자르기</li>
</ul>
<p>처음에는 단순히 데이터 수를 늘리는 것만 생각했다.</p>
<p>하지만 증강 과정에서 좌표가 어긋나면 원본 데이터보다 더 큰 문제가 생길 수 있다고 판단했다.</p>
<p>그래서 좌표가 크게 달라지는 회전은 최소한으로 적용했고, 좌우 반전이나 밝기 조정처럼 비교적 안전한 증강을 중심으로 사용했다.</p>
<p>증강 결과를 만든 뒤에는 일부 이미지를 직접 열어 바운딩 박스가 객체를 제대로 감싸고 있는지도 확인하였다. (이렇게 변환을 하고 무조건 확인하는 작업을 거쳐야만 추후의 작업에서 발생하는 오류를 최소화 할 수 있음을 정말정말 몸소 뼈져리게 느끼고 있는중...)</p>

<h2 id="4-입력-이미지-크기-통일">4. 입력 이미지 크기 통일</h2>
<p>YOLO 계열 모델의 비교 학습에서는 입력 이미지 크기를 <code>640×640</code>으로 맞췄다.</p>
<p>원본 데이터 중에는 <code>1920×1080</code> 이미지도 있었고, 직접 수집한 데이터는 또 다른 해상도를 사용했다.</p>
<p>이미지 크기가 제각각이어도 학습 과정에서 자동으로 resize를 할 수 있지만, 프로젝트에서는 전처리 단계에서 이미지와 라벨을 함께 관리하기 위해 별도의 코드를 이용하여 변환작업을 거쳐 조건을 통일 시켰다.</p>
<p>이때 가장 고민했던 부분은 단순 리사이즈와 크롭이었다.</p>
<p>가로로 긴 도로 영상을 정사각형으로 바로 줄이면 원본 비율이 달라질 수 있다. 반대로 특정 영역만 잘라내면 사용하려는 객체가 이미지 밖으로 잘릴 수 있었다.</p>
<p>실제 자전거 주행 영상에서도 위험요소의 위치는 서로 달랐다.</p>
<pre><code class="language-text">가까운 crack, pothole  → 화면 하단
멀리 있는 manhole     → 화면 중앙
전방의 bollard         → 화면 중앙 또는 상단</code></pre>
<p>도로 하단만 크게 자르면 가까운 균열은 잘 보일 수 있지만, 전방의 맨홀이나 볼라드를 미리 탐지하기 어려워질 수 있다.</p>
<p>그래서 처음부터 한 가지 크롭 방식을 고정하지 않고, 여러 후보 이미지를 만든 뒤 실제 영상에서 비교하는 방향으로 정리했다.</p>

<h2 id="5-학습·검증·테스트-데이터-분할">5. 학습·검증·테스트 데이터 분할</h2>
<p>클래스별 데이터를 정리한 뒤에는 학습용, 검증용, 테스트용으로 나눴다.</p>
<pre><code class="language-text">train : 70%
val   : 20%
test  : 10%</code></pre>
<p>클래스당 2만 장을 기준으로 다음과 같이 분할했다.</p>
<pre><code class="language-text">train : 14,000장
val   :  4,000장
test  :  2,000장</code></pre>
<p>이 과정에서 가장 중요하게 본 것은 이미지와 라벨이 항상 같은 분할에 들어가는 것이었다.</p>
<p>이미지는 <code>train</code> 폴더에 있는데 라벨은 <code>val</code> 폴더에 들어가면 해당 데이터는 정상적으로 사용할 수 없다.</p>
<p>또한 같은 이미지나 거의 같은 이미지가 train과 test에 동시에 들어가지 않도록 주의했다.</p>
<p>당시에는 파일명을 기준으로 데이터를 무작위 분할했다.</p>
<p>하지만 나중에 균열 데이터의 중복 문제를 겪으면서, 파일명이 다르다고 해서 반드시 서로 다른 이미지라고 볼 수는 없다는 사실을 알게 됐다.</p>
<p>무엇보다도 원천 데이터를 증강하기 전에 먼저 train, validation, test로 분할하고, 그중 train 데이터에만 증강을 적용하는 것이 더 안전한 방식이었다.</p>
<p>당시에는 전체 데이터를 먼저 증강한 뒤 분할했기 때문에, 원본에서 파생된 비슷한 이미지가 train과 test에 동시에 들어갈 가능성이 있었다.</p>
<p>이 부분은 이후 모델 테스트에서 큰 시행착오로 이어졌다.</p>
<p>원천 데이터 검수를 한 번 더 꼼꼼하게 했어야 한다는 사실을 나중에 정말 뼈저리게 느꼈다.</p>
<p>슬픈 소식의 예고편을 여기서 살짝 띄워본다.... coming soon....</p>

<h2 id="6-yolo-학습-데이터셋-구축">6. YOLO 학습 데이터셋 구축</h2>
<p>YOLO 학습용 데이터셋은 다음 구조로 구성했다.</p>
<pre><code class="language-text">dataset
├── images
│   ├── train
│   ├── val
│   └── test
├── labels
│   ├── train
│   ├── val
│   └── test
└── data.yaml</code></pre>
<p><code>images</code> 폴더에는 실제 이미지가 들어가고, <code>labels</code> 폴더에는 같은 이름의 <code>.txt</code> 라벨이 들어간다.</p>
<pre><code class="language-text">images/train/road_001.jpg
labels/train/road_001.txt</code></pre>
<p><code>data.yaml</code>에는 데이터 경로와 클래스 이름을 작성했다.</p>
<pre><code class="language-yaml">path: D:/Hanium_Bike_AI/05_datasets/YOLO_640_FINAL_5CLASS

train: images/train
val: images/val
test: images/test

names:
  0: manhole
  1: pothole
  2: flood_area
  3: bollard
  4: crack</code></pre>
<p>이 파일의 클래스 순서가 실제 라벨의 <code>class_id</code>와 다르면 모든 학습 결과가 잘못 해석될 수 있다.</p>
<p>따라서 학습을 시작하기 전에 샘플 이미지에 바운딩 박스를 그려 클래스 이름이 제대로 표시되는지 먼저 확인했다.</p>

<h2 id="7-coco-학습-데이터셋-구축">7. COCO 학습 데이터셋 구축</h2>
<p>이번 프로젝트에서는 YOLO만 학습하려는 것이 아니었다.</p>
<p>YOLOv8m과 YOLO11m뿐 아니라 RT-DETR-L, EfficientDet-D3, RetinaNet, Faster R-CNN 등 구조가 다른 객체 탐지 모델을 같은 데이터로 비교하려고 했다.</p>
<p>사실은  RT-DETR-L, EfficientDet-D3 를 순차적으로 가장 테스트 하고 싶었지만 환경을 어렵게 갖추고 테스트 했는데 GPU성능 문제로 계속 오류가 발생해 포기하고 이후 대안으로 RetinaNet, Faster R-CNN 을 결정했다. 추후에 FCOS도 추가하여 CNN계열 알고리즘의 비교를 조금더 명확하게 해보기 위해 노력하였다. 
<img alt="" src="https://velog.velcdn.com/images/addung/post/69bd8570-b62c-4ada-bbee-d987d1168f7b/image.png" /></p>
<p>문제는 모델마다 기본적으로 사용하는 데이터 형식이 달랐다는 점이다.
<img alt="" src="https://velog.velcdn.com/images/addung/post/6512bec5-7da1-4cc8-9f58-5aa126404b79/image.png" /></p>
<p>YOLO는 이미지마다 개별 <code>.txt</code> 라벨을 사용하지만, COCO 형식은 여러 이미지와 객체 정보를 하나의 JSON 파일에 저장한다.
<img alt="" src="https://velog.velcdn.com/images/addung/post/8cbddf90-7383-4199-b870-3ca8a9bec245/image.png" /></p>
<pre><code class="language-text">coco
├── images
│   ├── train
│   ├── val
│   └── test
└── annotations
    ├── instances_train.json
    ├── instances_val.json
    └── instances_test.json</code></pre>
<p>같은 원본 데이터를 YOLO와 COCO 형식으로 각각 변환해 두면, 모델이 달라도 학습 데이터 자체는 동일하게 유지할 수 있다.</p>
<p>모델 비교에서는 이 조건이 중요했다.</p>
<p>데이터셋이 다르면 성능 차이가 모델 구조 때문인지, 데이터 차이 때문인지 구분하기 어렵기 때문이다.</p>

<h2 id="9-객체-탐지-모델별-학습-환경-구성">9. 객체 탐지 모델별 학습 환경 구성</h2>
<p>데이터셋을 만든 뒤에는 구조가 다른 여러 객체 탐지 모델을 비교 대상으로 정했다.</p>
<h3 id="가-yolov8m">가. YOLOv8m</h3>
<p><img alt="" src="https://velog.velcdn.com/images/addung/post/754ee535-03d2-4386-b68b-a383dd6d2580/image.png" />
프로젝트의 기준 모델로 사용했다.</p>
<p>Ultralytics 환경에서 학습과 추론이 비교적 간단했고, 학습 결과와 시각화 자료도 자동으로 생성돼 전체 파이프라인을 확인하기에 적합했으며 결정적인 요인은 bbox형태의 객체 인식의 정확도와 속도 측면이었다.</p>
<h3 id="나-yolo11m">나. YOLO11m</h3>
<p>YOLOv8m과 같은 계열의 모델로, 동일한 데이터와 비슷한 조건에서 성능 차이를 확인하기 위해 추가했다. 최신모델이라고 하여 사용하였지만 속도면에서 8시리즈가 우위를 가져갔다. (테스트는 실제 자전거 주행 테스트 베드 영상을 기반으로 동일 조건에서 테스트. 추후 블로그에도 비교결과 기록 예정)</p>
<h3 id="다-rt-detr-l">다. RT-DETR-L</h3>
<p><img alt="" src="https://velog.velcdn.com/images/addung/post/0d7cd694-b198-41d8-860a-88fd9c604feb/image.png" /></p>
<p>Transformer 기반 객체 탐지 모델과 YOLO 계열 모델의 차이를 비교하기 위해 선택했다. GPU이슈로 학습 중단.</p>
<h3 id="라-efficientdet-d3">라. EfficientDet-D3</h3>
<p>YOLO와 다른 구조의 객체 탐지 모델을 비교하기 위한 후보였다. GPU이슈로 학습 중단.</p>
<h3 id="마-retinanet">마. RetinaNet</h3>
<p>One-stage detector 계열에서 Focal Loss를 사용하는 모델의 성능을 확인하기 위해 추가했다.</p>
<h3 id="바-faster-r-cnn">바. Faster R-CNN</h3>
<p><img alt="" src="https://velog.velcdn.com/images/addung/post/80b5dd65-f95d-4568-a681-d45bbb508158/image.png" />
<img alt="" src="https://velog.velcdn.com/images/addung/post/afaaffed-b910-4516-b33f-fd25bcdbc133/image.png" />
<img alt="" src="https://velog.velcdn.com/images/addung/post/6a684180-b959-422e-bf77-e21dddc7ed7d/image.png" /></p>
<p>Two-stage detector 계열의 대표 모델로, YOLO 계열과 정확도 및 추론 속도를 비교하기 위해 테스트했다.</p>
<p>모든 모델의 학습 조건을 완전히 동일하게 맞추기는 어려웠다.</p>
<p>모델마다 요구하는 이미지 크기와 GPU 메모리 사용량이 달랐기 때문이다.</p>
<p>예를 들어 YOLOv8m은 <code>640×640</code>, batch 4로 학습했지만 RT-DETR-L은 GPU 메모리 때문에 batch 1을 사용했다. EfficientDet-D3는 <code>896×896</code> 입력 크기를 사용했다.</p>
<p>그래서 결과만 한 줄로 놓고 순위를 매기기보다 다음 조건을 함께 기록하기로 했다.</p>
<ul>
<li>같은 원본 데이터셋을 사용했는가</li>
<li>동일한 train, val, test 분할을 사용했는가</li>
<li>입력 이미지 크기는 얼마인가</li>
<li>batch 크기는 얼마인가</li>
<li>학습 epoch 또는 step은 얼마인가</li>
<li>추론 속도는 어떤 조건에서 측정했는가</li>
</ul>

<h3 id="사-fcos">사. FCOS</h3>
<p>Anchor-Free 방식의 one-stage 객체 탐지 모델도 비교해보고 싶은 마음에 FCOS를 추가했다.</p>
<p>FCOS는 미리 정의된 anchor box를 사용하지 않고, 객체의 중심 위치와 경계까지의 거리를 직접 예측하는 구조다.</p>
<p>YOLO 계열, RetinaNet, Faster R-CNN과 탐지 방식에 차이가 있기 때문에, 같은 데이터셋에서 성능과 추론 결과가 어떻게 달라지는지 확인하기 위해 테스트했다. </p>

<h2 id="10-데이터-전처리-자동화">10. 데이터 전처리 자동화</h2>
<p>데이터 수가 많아지면서 파일을 하나씩 열어 확인하는 방식에는 한계가 있었다.</p>
<p>그래서 이미지와 라벨을 변환하고 결과를 확인할 수 있는 전처리 프로그램을 만들었다.</p>
<p>주요 기능은 다음과 같았다.</p>
<ul>
<li>원본 이미지와 JSON 불러오기</li>
<li>바운딩 박스 좌표 변환</li>
<li>640×640 이미지 생성</li>
<li>YOLO txt 생성</li>
<li>COCO JSON 생성</li>
<li>증강 이미지 생성</li>
<li>샘플 미리보기</li>
<li>실패 파일 로그 저장</li>
</ul>
<p>전처리를 자동화했지만, 프로그램이 결과를 만들었다고 바로 신뢰하지는 않았다.</p>
<p>좌표 변환 코드에 작은 오류가 있어도 수만 장의 라벨이 동시에 잘못될 수 있기 때문이다.</p>
<p>이때문에 변환 후에는 랜덤 샘플을 뽑아 이미지 위에 박스를 다시 그려 보는 검증 단계를 넣었다.</p>
<p>이 경험을 통해 자동화에서 중요한 것은 단순히 작업 시간을 줄이는 것뿐 아니라, 결과를 다시 확인할 수 있는 검증 기능을 함께 만드는 것이라는 점을 깨닫게 되었다.</p>
<p>무엇보다 AI학습에서는 정말이지, 내가 원하는 프로젝트에 목적성에 적합한 질좋은 데이터를 잘 가공하여 분류작업한뒤에 학습하는것이 정말정말 중요하다는 사실을 프로젝트를 하는 6-7월 두달 내내 뼈저리게 느끼고 있는중이다... (눈물이 앞을 가립니다...)</p>

<h2 id="11-데이터셋-검수-및-오류-점검">11. 데이터셋 검수 및 오류 점검</h2>
<p>처음에는 학습 시간이 가장 오래 걸릴 것이라고 생각했다.</p>
<p>실제로 모델 하나를 학습하는 데 하루 이상 걸리기도 했다. (우선은 각 모델별 비교를 위해서 30 epoch로 기준을 통일하였음)</p>
<p>하지만 초기 프로젝트에서 더 많은 시간을 사용한 것은 데이터셋을 준비하고 검증하는 과정이었다.</p>
<p>특히 다음 작업은 자동화만으로 끝나지 않았다.</p>
<ul>
<li>클래스 매핑 확인</li>
<li>손상된 이미지와 JSON 제거</li>
<li>이미지와 라벨 쌍 확인</li>
<li>증강 후 바운딩 박스 확인</li>
<li>train, val, test 중복 확인</li>
<li>YOLO와 COCO 변환 결과 비교</li>
<li>클래스별 개수 재확인</li>
</ul>
<p>데이터셋 폴더가 완성돼 보이더라도 내부 라벨이 올바르다는 보장은 없었다.</p>
<p>이때는 아직 몰랐지만, 이후 실제 주행 테스트에서 발생한 성능 문제도 결국 데이터 중복과 라벨 오류로 이어졌다...(이후에 엄청난 대참사 발생 예정)</p>

<h2 id="12-데이터-파이프라인-구축-결과">12. 데이터 파이프라인 구축 결과</h2>
<p>이번 작업은 공개 데이터셋을 내려받아 YOLO 학습 명령어만 실행한 것이 아니었다.</p>
<p>서로 다른 출처와 형식의 데이터를 하나의 학습 기준으로 통합하고, 여러 모델에서 재사용할 수 있도록 전처리 파이프라인을 만든 과정이었다.</p>
<pre><code class="language-text">원본 데이터 분석
    ↓
클래스 매핑
    ↓
이미지 및 라벨 정제
    ↓
클래스별 수량 균형화
    ↓
이미지 증강과 bbox 동기화
    ↓
train / val / test 분리
    ↓
YOLO 형식 변환
    ↓
COCO 형식 변환
    ↓
샘플 시각화 검증
    ↓
모델별 학습 환경 연결</code></pre>
<p>모델 학습 결과는 한 줄의 mAP 수치로 보이지만, 그 결과를 만들기 위해 데이터가 어떤 과정을 거쳤는지 설명할 수 있어야만 했다.</p>
<p>이번 작업을 통해 객체 탐지 프로젝트에서는 모델 선택만큼이나 데이터 전처리 파이프라인과 검증 과정이 중요하다는 것을 직접 경험했다.</p>

<p>특히 YOLOv8m은 평가 데이터에서 높은 Precision, Recall, mAP를 기록했다.</p>
