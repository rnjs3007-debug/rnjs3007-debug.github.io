<p>데이터셋 경로를 연결하고, <code>data.yaml</code>을 작성하고, 학습된 모델이 이미지에서 객체를 찾아 바운딩 박스를 그리는 것까지 확인했다.<br />처음 결과 화면을 봤을 때는 이제 데이터만 충분히 모아서 학습하면 될 것이라고 생각했다!</p>
<p>그런데 실제 프로젝트를 진행해 보니, 모델을 돌리는 것보다 먼저 정해야 할 문제가 있었다.</p>
<blockquote>
<p><strong>우리 모델이 자전거도로에서 정확히 무엇을 탐지해야 하는가?</strong></p>
</blockquote>
<p>처음에는 다양한 위험요소를 최대한 많이 탐지하는 방향으로 생각했다.<br />하지만 탐지 대상을 늘린다고 해서 AI성능이 무조건 좋아지는 것은 아니라는 사실!</p>

<h2 id="1-장애물을-obstacle-클래스로-묶기">1. 장애물을 obstacle 클래스로 묶기</h2>
<p><img alt="" src="https://velog.velcdn.com/images/addung/post/17fc254d-db87-4fdc-ac71-ee7fc0121895/image.png" /></p>
<p><img alt="" src="https://velog.velcdn.com/images/addung/post/eff3f669-ec4e-4477-aa73-bf6f3be0faad/image.png" /></p>
<p>초기에는 자전거도로 위에 놓인 박스, 물통, 전동킥보드와 같은 물체를 모두 <code>obstacle</code>이라는 하나의 클래스로 묶는 방향을 생각했다.</p>
<pre><code class="language-text">obstacle
├── box
├── water_container
└── kickboard</code></pre>
<p>처음에는 이 방식이 단순하고 관리하기도 쉬워 보였다.</p>
<p>어차피 모두 자전거 주행을 방해하는 물체이니, 모델이 구체적인 종류까지 구분하지 않고 <strong>“앞에 장애물이 있다”</strong>고만 판단해도 괜찮을 것이라고 생각했다.</p>
<p>하지만 교수님 피드백을 반영하며 다시 생각해 보니 문제가 있었다.</p>
<p>박스와 킥보드는 형태가 전혀 다르고, 실제 도로에서 차지하는 크기나 위험성도 다르다.<br />서로 다른 모양의 객체를 하나의 클래스로 묶으면 모델이 그 클래스의 공통된 특징을 배우기 어려울 수 있었다.</p>
<p>결국 통합된 <code>obstacle</code> 클래스는 사용하지 않고, 각각을 독립된 클래스로 나누기로 했다.</p>

<h2 id="3-볼라드-누락-발생">3. '볼라드' 누락 발생</h2>
<p>클래스를 정리한 뒤 다시 자전거도로 환경을 살펴보면서, 한 가지 중요한 대상이 빠져 있다는 것을 알게 됐다.</p>
<p>바로 <code>bollard</code>, 차량 진입을 막기 위해 설치된 볼라드였다.</p>
<p>볼라드는 정상적으로 설치돼 있어도 자전거가 피해야 하는 고정 시설물라는 판단이 들었다. 테스트베드를 기반으로 자전거를 타면서 유심히 살펴보니 상대적으로 간격이 좁은 볼라드는 자전거 주행시에 꽤나 위험한 요소라고 판단되었다.
특히 야간이나 시야가 좋지 않은 상황에서는 충돌 위험이 있기 때문에 프로젝트의 탐지 대상으로 포함할 필요가 있었다.</p>
<p>그래서 기존 7개 클래스에 볼라드를 추가한 '8개 클래스 구성'도 검토했다.</p>
<pre><code class="language-text">manhole
pothole
flood_area
box
water_container
kickboard
trash_pile
bollard</code></pre>

<h2 id="4-과다-클래스-문제">4. 과다 클래스 문제</h2>
<p><img alt="" src="https://velog.velcdn.com/images/addung/post/754ee535-03d2-4386-b68b-a383dd6d2580/image.png" /></p>
<p>클래스 구성을 늘리면서 한 가지 고민이 생겼다.</p>
<p>박스, 물통, 킥보드, 쓰레기더미를 모두 별도의 클래스로 유지하려면 각 클래스마다 충분한 데이터를 확보해야 한다.<br />또한 실제 주행 테스트에서 해당 객체가 등장해야 모델의 성능도 확인할 수 있다.</p>
<p>하지만 우리 프로젝트의 테스트베드는 사천과 진주의 자전거도로였다.</p>
<p>실제 도로에서 맨홀이나 포트홀, 균열, 볼라드는 비교적 자주 확인할 수 있었지만, 박스나 물통, 킥보드, 쓰레기더미는 항상 나타나는 대상이 아니었다.</p>
<p>학습 데이터는 만들 수 있어도 테스트베드에서 충분히 검증하기 어려운 클래스라면, 프로젝트의 핵심 기능과 거리가 생길 수 있었다.</p>
<p>이 과정에서 처음에는 “많이 탐지하는 모델”을 만들려고 했지만, 점점 “실제 자전거 주행에서 중요한 위험요소를 제대로 탐지하는 모델”을 만드는 쪽으로 방향이 변경하며 구체적으로 잡아갔다.</p>

<h2 id="5-6개-클래스-학습">5. 6개 클래스 학습</h2>
<p>최종 5개 클래스로 바로 넘어간 것은 아니었다.</p>
<p>위의 결정을 한것에 있어서는 다음의 경험도 굉장히 큰 역할을 하였다. 다음과 같은 6개 클래스 데이터셋도 구성해보았었다.</p>

<p>이 단계에서는 <code>box</code>, <code>kickboard</code>, <code>trash_pile</code>을 제외하고, 대신 노면 균열인 <code>crack</code>과 볼라드인 <code>bollard</code>를 포함했다.</p>

<h2 id="7-클래스-변경-과정">7. 클래스 변경 과정</h2>
<p>처음에는 클래스 이름 몇 개만 수정하면 끝날 것이라고 생각했다.</p>
<p>하지만 객체 탐지 데이터셋에서 클래스 구성을 바꾸면 함께 수정해야 하는 것이 너무 많았음... </p>
<ul>
<li>원본 데이터 폴더</li>
<li>클래스별 이미지 선별</li>
<li>라벨의 <code>class_id</code></li>
<li>YOLO 형식의 <code>.txt</code> 파일</li>
<li>COCO 형식의 JSON</li>
<li><code>data.yaml</code></li>
<li>학습·검증·테스트 폴더</li>
<li>서버에 전달할 클래스 이름</li>
<li>기존에 작성한 변환 코드</li>
<li>결과를 비교하는 평가 코드</li>
</ul>
<p>특히 기존 클래스 순서가 바뀌면 같은 숫자가 전혀 다른 객체를 의미할 수 있다.</p>
<p>예를 들어 이전 데이터에서 <code>3</code>이 <code>box</code>를 의미했는데, 최종 데이터에서는 <code>3</code>이 <code>bollard</code>를 의미한다.<br />이 상태에서 예전 라벨을 그대로 섞으면 모델은 박스를 볼라드로 배우게 된다.</p>
<pre><code class="language-text">이전 class_id 3 → box
최종 class_id 3 → bollard</code></pre>
<p>이때부터 데이터셋을 합치기 전에 이미지 수만 확인할 것이 아니라, 각 라벨 파일 안의 클래스 번호가 현재 <code>data.yaml</code>과 일치하는지도 확인해야 한다는 것을 알게 됐다.
수정하게되면 AI데이터셋의 무한 검토에 빠지게되었음.</p>
<p>나중에 실제 학습 성능이 무너졌을 때도 클래스 번호와 라벨 구성은 중요한 원인 후보가 됐다.</p>
<hr />
<h2 id="8-클래스-선정과정에서-배운점">8. 클래스 선정과정에서 배운점.</h2>
<p>이번 단계에서는 아직 모델 성능을 높이는 것보다, 탐지 문제 자체를 정의하는 과정에 가까웠다.</p>
<p>처음에는 탐지 클래스가 많을수록 좋은 프로젝트라고 생각했다.<br />하지만 실제로는 다음 조건을 함께 고려해야 했다.</p>
<ol>
<li>자전거 주행 안전과 직접 관련이 있는가?</li>
<li>충분한 학습 데이터를 확보할 수 있는가?</li>
<li>실제 테스트베드에서 검증할 수 있는가?</li>
<li>다른 클래스와 형태가 지나치게 겹치지 않는가?</li>
<li>결과를 앱과 서버에서 실제로 활용할 수 있는가?</li>
</ol>
<p>무엇을 학습할지 명확하지 않은 상태에서는 모델을 아무리 오래 학습해도 의미 있는 결과를 얻기 어렵다는 사실이었다.</p>
<p>돌이켜 보면 이때 클래스 구성을 여러 번 바꾼 것은 시행착오였지만, 프로젝트의 목표를 구체적으로 정리하는 데 정말 필요한 과정이었다는 생각도 든다. 무엇보다 실제 테스트베드를 먼저 꼼꼼하게 체크한뒤에 결정하는게 맞다는 명확한 사실도!</p>
